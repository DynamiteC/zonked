# Browser matrix

Three engines (Chromium, Firefox, WebKit) at three viewports (1280x800 desktop, 390x844 iPhone-like, 412x915 Android-like), 18 checks each, 162 checks in total. Run it with:

```bash
node web/scripts/browser-matrix.mjs
```

The script builds HEAD in a throwaway git worktree under the system temp dir, serves it with `vite preview`, runs every check, removes the worktree and exits non-zero on any failure. It writes `.work/matrix/results.json`, `.work/matrix/matrix.log` and failure screenshots to `.work/matrix/shots/`. It refreshes only the block between the two marker comments below. Set `MATRIX_ONLY=firefox` or `MATRIX_ONLY=chromium:phone-ios` to run a subset.

Engine builds are the ones Playwright installs. They are test builds, not the shipping browsers. The iPhone-like and Android-like runs set viewport, touch and (Chromium and WebKit only) the mobile flag. They do not change the engine, the user agent hardware or the audio stack. Firefox has no mobile emulation in Playwright, so it gets touch only. Firefox runs with its content sandbox off, because it crashes on the test Mac otherwise. That points to the test host, not the app.

Result: 150 of 162 pass. Chromium 51 of 54, WebKit 51 of 54, Firefox 48 of 54. Two problems explain all 12 failures.

## Failure analysis

Line numbers refer to the commit named in the generated block. Files under `web/src/ui/calm` change often, so search for the quoted text if a line moved.

### 1. No AudioWorklet: the screen says only "Stopped." (all 9 runs)

- Test: `AudioWorkletNode`, `AudioWorklet` and `audioWorklet` removed before page scripts run. The user accepts the notice and taps play.
- Seen: no crash, no blank screen, no uncaught error. The engine goes to state `error` (`web/src/audio/engine.ts` line 79, the catch around `ctx.audioWorklet.addModule` at line 86). The Calm status line shows `Stopped.` (`web/src/ui/calm/CalmApp.tsx` line 116). The error text never reaches the screen.
- Console text: none. The error is caught and stored in the engine status.
- Screenshots: `.work/matrix/shots/chromium-desktop-fallback-no-audioworklet.png`, `.work/matrix/shots/firefox-desktop-fallback-no-audioworklet.png`, and the same name pattern for the other engine and viewport pairs (`webkit-phone-ios-...`, `webkit-phone-android-...`, `chromium-phone-ios-...`). Each file name is `<engine>-<viewport>-fallback-no-audioworklet.png`.
- Cause: the Calm screens read `snap.playing`, not `engine.status.error`.
- Minimal fix: in `CalmApp.tsx` near line 116, when `engine.status.state === 'error'`, render one plain line such as "This browser cannot play Zonked sound. Try a current Chrome, Firefox or Safari." in the same `role="status"` element. No engine change needed.
- Real-world weight: low. Every current engine has AudioWorklet. It matters for old browsers.

### 2. Firefox: the Rain loop never starts (3 of 3 Firefox runs)

- Test: tap Rain on the Nature screen.
- Seen: nothing happens. The message line stays empty and `window.__zonked.nature.id` stays null. Synth sounds in the same run work. A direct probe in the page fetched `/samples/rain.mp3.json` (an MP3 with an ID3 header) and `decodeAudioData` did not settle in 10 s.
- Console text: none.
- Screenshots: `.work/matrix/shots/firefox-desktop-nature-loop-mp3.png`, `.work/matrix/shots/firefox-phone-ios-nature-loop-mp3.png`, `.work/matrix/shots/firefox-phone-android-nature-loop-mp3.png`.
- Likely cause, two parts. (a) This Firefox test build probably has no MP3 decoder on this Mac. That is not proven: it was not tried in a release Firefox. (b) The app has a real gap either way: `bus.ctx.decodeAudioData(bytes)` in `web/src/audio/samples/layer.ts` line 58 has no timeout, so a decoder that never answers leaves the user with no message. The existing message at line 62 only fires on a rejected promise.
- Minimal fix: race the decode against a timer of about 10 s and return the existing `sample unavailable` result when the timer wins.
- Next step: run `MATRIX_ONLY=firefox node web/scripts/browser-matrix.mjs` on a Mac with a release Firefox install (point Playwright at it) to settle part (a).

## What passes everywhere

First load with no console errors, skip path, no AudioContext before the safety notice, sound starts with peak above 0, Stop takes at least 250 ms to reach stopped, synth sounds, Crew demo (beat changed, for example 40 Hz to 18 Hz), theme switch, reload keeps state, service worker activates, offline reload, zero requests outside the origin, reduced motion, and the wake lock, MediaSession and SharedArrayBuffer fallbacks (sound still plays, no uncaught error, and with no SharedArrayBuffer the engine reports `usesSharedMemory: false`).

## Not testable here

- Real iOS Safari. Playwright WebKit is a desktop WebKit build. It does not share iOS audio session rules, the silent switch, background audio limits, autoplay rules after a screen lock, or the iOS PWA home-screen mode. A pass here does not prove iOS Safari.
- Real Android Chrome. The Android-like runs are a desktop Chromium with a 412x915 window. They do not cover real touch hardware, the Android audio stack, battery savers, or the install prompt.
- Bluetooth audio: latency, codec switching and dropouts.
- Lock screen and background: MediaSession controls on a locked phone, wake lock behaviour, and audio when the tab is hidden for a long time.
- Real speakers or headphones. The checks read the engine's own peak and state. Nobody listened.
- Release Firefox and Safari builds, and any browser older than the Playwright builds above.
- Crew Synced over the loopback bridge. The Crew check uses the built-in demo only.
